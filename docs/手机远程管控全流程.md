# 手机远程管控全流程：从「让电脑控手机」到「远程切卡 + 验证码回传」

> 一套完整可复现的方案：Windows 笔记本 → Mac（USB 连 iPhone）→ NAS/华为云推送栈 → 2999 控制台。
> 覆盖四段能力：**① 给电脑控手机的权限 ② 电脑在手机上写快捷指令/自动化 ③ 做页面 + 多通道通知 ④ 真实验证码回传**。
> 最后更新：2026-11-17（iPhone SE3 / iOS 27.2.1 / 375x667 点）

---

## 0. 全景

```
        ┌─────────────┐  USB   ┌──────────────┐   LAN    ┌───────────────┐
        │  iPhone     │◄──────►│  Mac         │◄────────►│  NAS 198.51.100.117 │
        │  iOS 27.2.1 │ 线     │ iphone-control│  ssh/HTTP│  3020 面板 + 2999 外壳 │
        └─────────────┘        └──────────────┘          └───────┬───────┘
              ▲                                                   │ PHONE_MASTER
              │ 信息自动化（门铃短信 #phone on HK）                 ▼
              └────────────────────────────────────────── 华为云 hw（主队列 3105）
                                                              │ apprise 门铃
                                                              │ 飞书「短信」群
```

三条链路各自独立，任何一条断了其余仍可用：

| 链路 | 用途 | 依赖 |
| --- | --- | --- |
| **A. 控制链** | 电脑点手机屏幕、装捷径、读屏 | USB 线 + Mac + iphone-control |
| **B. 执行链** | 远程切卡（无人值守） | 手机自动化 + 门铃短信 + 推送栈 |
| **C. 回传链** | 结果/验证码回到你手上 | 捷径 GET 回报 + 飞书群 |

## 1. 让电脑能控手机：四条路怎么选

给 iOS 设备做自动化，堵点从来不是「有没有 API」，而是**签名**。四条路的取舍：

| 方案 | 需要签名 | Windows | macOS Intel | 能点屏幕 | 结论 |
| --- | --- | --- | --- | --- | --- |
| iPhone 镜像（macOS 15+） | 否 | ✗ | ✓ | 间接 | 要求 iPhone 与 Mac **同一 Apple ID**，跨区账号直接死 |
| Xcode + WebDriverAgent | **是**（免费 Apple ID） | ✗ | ✓ | ✓ | 装 Xcode 15GB / 40–90 分钟；免费证书 7 天过期，得反复重签 |
| go-ios | 部分 | ✓ | ✓ | **✗** | 读设备/装包/截图/启动 App 都能做，**但没有可用的点按后端**（`ui status` 报 `no UI automation backend reachable`）；装 DeviceKit/WDA 又要签名 |
| **iphone-control**（`Derrors/iphone-control`） | **否** | ✗（无 win 包） | 需源码编译 | ✓ | **iOS 27+ 走原生控制**：无障碍读屏 + HID 注入 + CoreDevice，不签名不要 Apple ID |

**选它。** iOS 27 起系统开放了无障碍树与 HID，这才是免签名的正路；iOS 17–26 只能退回 WDA。

### 1.1 装（macOS，x86_64 走源码编译）

官方只发 Linux / macOS-arm64 包。Intel Mac 上：

```bash
# 1) 命令行工具（没有 Xcode 也能装，无 GUI）
sudo softwareupdate --list | grep "Command Line Tools"
nohup sudo softwareupdate -i "Command Line Tools for Xcode-16.2" > /tmp/clt.log 2>&1 &
xcode-select -p          # 完成判据：/Library/Developer/CommandLineTools
clang --version

# 2) Rust
curl --proto '=https' --tlsv1.2 -sSf https://sh.rustup.rs -o /tmp/rustup.sh
sh /tmp/rustup.sh -y --profile minimal --default-toolchain stable

# 3) 源码（Windows 上 curl codeload 会 SSL 失败，用 gh api 取 tarball 再 scp 过来）
gh api repos/Derrors/iphone-control/tarball/v0.2.7 > ic-src.tgz
tar xzf ic-src.tgz && cd Derrors-iphone-control-*/

# 4) 编译（Intel 约 9 分钟）
cargo install --path apps/iphone-control --locked
ls -l ~/.cargo/bin/iphone-control     # 25 MB

# 5) 起守护进程
pkill -f "goios/ios"; pkill -f AltServer      # 不能和 go-ios / AltServer 同时跑，都抢 usbmuxd
export PATH=$HOME/.cargo/bin:$PATH
nohup iphone-control daemon > /tmp/ic_daemon.log 2>&1 &
iphone-control status                          # 目标：状态 就绪
```

### 1.2 三个必踩的坑

1. **开发者镜像挂载冲突**（`cryptexd routine install failed: ... /System/Developer [17: File exists]`）
   → 之前用 go-ios 挂过 DDI 了。`~/goios/ios image unmount` → 杀掉 daemon 重启，`status` 变「就绪」。
2. **`doctor` 里会长期显示旧报错**：日志是追加的，10:12 那条错误不会消失，判据只认 `状态 就绪` + 实际工具调用成功。
3. **`iphone_type_text` 偶发超时**（`rmcp::service: timed out draining in-flight responses`）
   → `pkill -f "iphone-control daemon"` 重启即恢复。别归因到输入法。

### 1.3 从别的机器驱动它（MCP over stdio）

`iphone-control mcp` 是个 stdio MCP server。用一条 `initialize + initialized + tools/call` 就能调：

```python
# ~/ic_call.py  ——  ssh mac 'python3 ~/ic_call.py iphone_tap "{\"x\":188,\"y\":562}"'
import json, os, subprocess, sys
tool = sys.argv[1]; args = json.loads(sys.argv[2]) if len(sys.argv) > 2 else {}
binary = os.path.expanduser("~/.cargo/bin/iphone-control")
init   = {"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2024-11-05",
          "capabilities":{},"clientInfo":{"name":"dsh","version":"1"}}}
inited = {"jsonrpc":"2.0","method":"notifications/initialized"}
call   = {"jsonrpc":"2.0","id":2,"method":"tools/call","params":{"name":tool,"arguments":args}}
payload = "\n".join(json.dumps(x) for x in (init, inited, call)) + "\n"
p = subprocess.run([binary,"mcp"], input=payload, capture_output=True, text=True, timeout=180)
for line in p.stdout.strip().splitlines():
    try: msg = json.loads(line)
    except Exception: continue
    if msg.get("id") == 2:
        for c in (msg.get("result") or {}).get("content", []):
            if c.get("type") == "text": print(c["text"])
            elif c.get("type") == "image":
                path = os.path.expanduser("~/ic_shot_%d.bin" % len(c.get("data","")))
                open(path,"wb").write(__import__("base64").b64decode(c["data"]))
                print("IMAGE saved", path)
```

批量连点要复用同一个 MCP 会话（`Popen` + 递增 id），否则每次调用要重新握手，慢十倍。

**17 个工具与实测参数名**（README 没写全，踩出来的）：

| 工具 | 参数 |
| --- | --- |
| `iphone_status` / `iphone_screenshot` | `{}` → 截图存 `~/ic_shot_<n>.bin`，返回 `375x667 点` |
| `iphone_list_elements` | `{"limit":N,"text":"过滤"}` |
| `iphone_tap` / `iphone_long_press` | `{"x","y"}` |
| `iphone_tap_element` | `{"text":"按钮文字"}` |
| `iphone_swipe` | `{"from_x","from_y","to_x","to_y"}` |
| `iphone_type_text` | `{"text":"…"}`（中文可用，会自动点「允许粘贴」） |
| `iphone_launch_app` | `{"app":"com.apple.shortcuts"}` ← 键名是 `app`，不是 bundle_id |
| `iphone_press_button` | `{"button":"home"}`（**不要用 lock**，锁了没人能解锁） |

## 2. 在手机上「写」快捷指令

### 2.1 三条硬规矩

1. **坐标只认 a11y 给的 `@(x,y)`**。`iphone_screenshot` 的预览宽度和设备点数不一致（预览约 420px、实际 375 点），照图目测点必错。
2. **能读元素就别读图**。捷径编辑器的画布其实能读到：`Button "蜂窝号码" id="enum" value="￼ HK"`、`Button "状态" id="stepper" value="关闭"`、`Button "URL" id="textInput"`；只有滚动中的一瞬间会退化成只剩底部工具条。
3. **`iphone_type_text` 对 URL 字段是从末尾追加**，点文本中间不会移动光标 → 会把 `https://` 变成 `thttps://`。清空要连点删除键（`Popen` 会话里循环 `iphone_tap {"x":349,"y":593}` N≈130 次）。

### 2.2 plist 生成这条路能走多远

`WFWorkflow` plist + `shortcuts sign -m anyone` 能一次成型**线性**捷径（下载、拆分、取值、设变量、URL 里插变量），但：

- **条件分支不可靠**：`conditional` 的 `WFInput` 必须 `Type=Variable` 包一层，裸 attachment 会被判「请为此操作中的每个参数选取值」；即使序列化正确，iOS 27 上 getitem 输出做字符串比较**恒不成立**（实测 zt5/zt6/zt7 全走 else）。→ 结论：**plist 里别写 If**，一条捷径只做一件事。
- 数据参数（`text.split` 的输入、`getitemfromlist` 的输入）用裸 `WFTextTokenAttachment` 可以；展示参数（`showresult` 的 `Text`）必须 `WFTextTokenString` + `\uFFFC` + `attachmentsByRange`。
- `UUID`/`GroupingIdentifier` 必须写在 `WFWorkflowActionParameters` 里，放 action 顶层会被导入器静默丢弃。
- **蜂窝动作（AppIntent）无法 plist 化**（参数键名未公开、entity 序列化未验证）→ 只能 UI 点。

### 2.3 导入捷径的唯一可用通道

`shortcuts://import-shortcut?url=…` 在这台机器上**一律报「提供的快捷指令URL无效」**（http 本地服务、GitHub raw 都试过；同一 URL 用 Safari 能正常下载，说明网络没问题，是 scheme 本身被拒）。

可用通道：Safari 打开 raw URL → 点「下载」→ 文件 App「最近项目」点该 `.shortcut` → 预览页点「添加快捷指令」→ 直接进编辑器。名字取自文件名（`WFWorkflowName` 也生效）。

### 2.4 iOS 26+ 的「自动化」新模型

自动化没有独立面板了，**写在捷径编辑器里**：

```
自动化 标签 → 右下 + → 动作库点性质分类「自动化」→ 选「信息」触发器
   → ⚠️ 默认那行是「发件人 是 []」，必须点成「信息 包含 [文本]」
      （不改会留下「配置"发件人"启用此自动化」的失效卡）
   → 填触发词 → 加动作「运行快捷指令」→ 选目标捷径
```

坑：选完分类后**直接在搜索框追加关键词**能得到正确过滤；如果先点搜索框把「自动化」token 清掉，会落到全局动作搜索（出的是「查找信息/删除信息」，不是触发器）。

自动化卡片长按菜单：`编辑快捷指令 / 自动化 / 运行前确认 / 删除`（**没有「复制」**，要复制只能进编辑器改）。

### 2.5 一次性授权（不点就静默不跑）

- 自动化里的「运行快捷指令」首次运行会弹「允许「运行快捷指令 N」运行另一个快捷指令吗？」
- 捷径里的「获取 URL 内容」首次运行会弹「允许「号码-X」连接 push.example.com 吗？」

被其它模态挡住时 iOS **不排队**，直接跳过这次执行。所以每条新建的捷径/自动化，**手动 ▶ 跑一次**把两个「允许」点掉。

## 3. 服务端：队列 + 页面

### 3.1 拓扑

- **hw（华为云）是主队列**，`systemctl status push-leg-hw`：3104 nginx → 3105 面板/API、3107 relay、3108 feishu。
- **NAS 3020 是同一份源码的第二副本**（`push-translator`），带 `PHONE_MASTER=https://push.example.com` 时 `/phone/*` 全部代理到 hw。
- 2999 控制台用 `panelproxy.py` 把 3020 的 pane 嵌进 iframe（`/numbers` → 3020 `/` + hash `#n`）。

> 起因：NAS ↔ hw 的 tailnet 双向不通（两侧 iptables 都 ACCEPT，疑 ACL），所以只让 NAS 单向出网去打 hw 的公网入口。

### 3.2 端点表

| 端点 | 谁用 | 鉴权 |
| --- | --- | --- |
| `GET /p/<token>/phone/pull[?fmt=text][&act=on\|off\|default]` | 手机捷径拉指令 | path token |
| `GET /p/<token>/phone/report?id=&ok=&detail=&act=&plan=` | 手机回报结果 | path token |
| `GET /p/<token>/phone/otp?code=&from=&text=` | 手机回报验证码 | path token |
| `GET /phone/state` `/phone/cmd?action=toggle\|default\|status&plan=X&on=1` `/phone/plans?data=` `/phone/otp?n=5` | 页面 | 公网必须 `ctl` 口令或 `x-phone-ctl` 头；**本机 127.0.0.1 免口令**（2999 反代过来天然合规） |

队列语义：`pending` →（手机 pull）`taken` →（report）`done`/`failed`；看门狗 150 秒把 `taken` 判失败并推飞书。

### 3.3 页面块（2999 `/numbers`）

`#nswap` 按 `role` 分级渲染：

- `switch`（CTE / HK / PH / giffgaff）→ 出「切为默认 / 开启 / 关闭」三个按钮
- `always_on`（US +1 208）→ 只显灰字「常开 · 不参与切换」
- `data_only`（dtcpay / Jetpac / First）→ 只显灰字「流量 · 不参与切换」

下面紧跟 `#notp`「短信验证码 · 最近」区块，`loadOtp()` 拉 `/phone/otp?n=6`。

### 3.4 手机端为什么必须「先关后开」

iOS **同时只能激活 2 条线路**。直接打开第三条会弹强制的「选取要关闭的电话号码」，自动化就卡死在那。所以每条捷径 = `关闭另外三条 → 打开目标 → 回报`。

另外一个致命点：`设定默认号码` 成功后系统必弹模态「默认设置已更改」（唯一按钮「好」），**这个模态会挡住下一次自动化的蜂窝操作**，远程指令静默不执行。→ 捷径里**不放设默认动作**；`切为默认` 按钮的实际语义就是「关掉其它 + 打开目标」。

## 4. 通知通道：不止短信

门铃目前用 iMessage（`POST apprise /notify/imessage_nas`），但**同一套机制换通道零改动**——因为门铃本质就是「一条能被手机自动化正则命中的文本」：

| 通道 | 手机端触发器 | 备注 |
| --- | --- | --- |
| iMessage / 短信 | 自动化「信息 包含 `#phone`」 | 当前方案，最稳（不依赖网络 App） |
| 飞书 / 企业微信 | 自动化「App 被打开」+ 通知 | 需要点通知，无人值守差一些 |
| Bark / ntfy / Telegram | 同上 | 手机装对应 App，用「App」触发器或通知扩展 |
| 邮件 | 自动化「电子邮件 包含」 | 延迟偏高 |
| 纯 HTTP 轮询 | 无自动化，捷径定时跑 | iOS 后台调度不可靠 |

Apprise 支持 100+ 服务，`APPRISE_URL/notify/<key>` 换 key 即可；本栈已配置 `imessage_nas`、`feishu`（短信群 `smsgrp`）。

**回传同理**：捷径结束时 `GET /p/<token>/phone/report` 或 `/otp`，服务端决定推到飞书/短信/Bark。

## 5. 验证码回传（服务端已上线，手机侧两条路线）

### 5.1 服务端（已完成并冒烟）

```bash
# 手机/脚本回传（token 在 URL 里，免口令）
curl "http://127.0.0.1:3105/p/<TOKEN>/phone/otp?code=123456&from=TestBank&text=your+code+is+123456"
# → {"ok": true, "stored": 1, "otp": {...}}

# 查询最近 6 条（页面用）
curl "http://127.0.0.1:3105/phone/otp?n=6"
```

存储：`phone-state.json` 的 `otp` 数组（最多 30 条，`code/from/text/at/src`），同时推飞书「短信」群 `🔑 验证码｜手机：**123456**，来自 TestBank（时间）`。

### 5.2 路线 A：自动化直传（推荐，零 Mac 依赖）

```
信息自动化（信息 包含 任意 / 或按来源筛选）
  → 捷径：取「快捷指令输入」→ GET /p/<TOKEN>/phone/otp?text=<输入>
  → 服务端正则提取 4–8 位数字 → 存库 + 推飞书
```

要点：**不要在捷径里做正则**（plist 序列化坑多、UI 配置繁琐），把原文整段发过来，服务端 `re.search(r"\b(\d{4,8})\b", text)` 提码即可。

⚠️ 这一段的实测被卡住：**2026-11-17 22:47 手机从 USB 掉线**（`doctor` 报 `❌ USB 上没有 iPhone/iPad`），插回线后 5 分钟可验收：建一条自动化 → 手动触发 → 看 `/phone/otp` 是否有新记录。

### 5.3 路线 B：电脑读屏兜底（手机在线时可用）

手机收到短信时，让 Mac 打开「信息」App 读最近会话的 a11y 文本，正则提码后回传：

```bash
python3 ~/ic_call.py iphone_launch_app '{"app":"com.apple.MobileSMS"}'
python3 ~/ic_call.py iphone_list_elements '{"limit":60}'   # 抓 Cell 文本里的 6 位数字
curl "http://<hw>/p/<TOKEN>/phone/otp?code=…&text=…"
```

适合「偶尔查一次」，不适合实时——每次都要唤醒手机 App。

### 5.4 如果 Mac 与 iPhone 是同一 Apple ID

可以开 **设置 → 信息 → 短信转发 → 勾选 Mac**，之后 Mac 的 `~/Library/Messages/chat.db` 里就有全部短信（`sqlite3` 直读，`text` 在 `message.text`，`attributedBody` 需解码）。这是最省力的方案，但本机 iPhone 与 Mac 是**不同 Apple ID**（`user@example.com` vs iPhone 主号），走不通。

## 6. 运维手册

### 6.1 改代码后必须做的三件事

```bash
python3 -m py_compile /vol1/1000/docker/apps/push/apprise/universal-push-proxy.py   # 两侧都编译
sudo systemctl restart push-translator      # NAS
sudo systemctl restart push-leg-hw          # hw
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:3020/   # 必须 200，不是 000
```

> 血泪：一次补丁把 emoji 写成 `\ud83d\udd12`（孤立代理对）→ `_reply_html` 的 `text.encode("utf-8")` 抛 `UnicodeEncodeError: surrogates not allowed` → 3020 根页整页 000、2999 502，而 `/phone/state`（JSON 分支）仍 200，很容易误判「服务是好的」。

### 6.2 备份约定

每次改动前 `cp universal-push-proxy.py universal-push-proxy.py.bak-<语义>-<时间>`，现有：`numswap / actfilter / phonefeishu / fuzzy / msg3 / msg4 / otp / otpui`。

### 6.3 验收一条指令

```bash
ssh hw "curl -s 'http://127.0.0.1:3105/phone/cmd?action=default&plan=HK'"
ssh hw "journalctl -u push-leg-hw --since '-2 min' | grep -E '\[phone\] (nudge|report|feishu|otp)'"
```

正常：10 秒内 `nudge sent` → `report matched by act/plan` → `feishu ok: ✅ 切换成功 | iPhone：卡1 固定 US；卡2 由 PH 切到 **HK**（手机已执行）`。

### 6.4 故障对照

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 飞书 ❌「对不上任何待执行指令」 | 回报的 plan/act 与队列不一致 | 核对捷径 URL 的 `detail`/`plan`；服务端有 plan 兜底匹配 |
| 飞书 ❌「…：未建捷径」 | 该卡没有捷径 | 复制一条改 4 处 |
| 队列 `pending` 不动 | 自动化关了 / 未授权 / 被「默认设置已更改」模态挡住 | 查开关 → 手动 ▶ 授权 → 点掉模态 |
| 捷径报「所选蜂窝号码当前未激活」 | 先设默认后开卡 | 必须先关后开 |
| 弹「选取要关闭的电话号码」 | 目标成了第三条激活线路 | 同上 |
| `doctor` 报 USB 没设备 | 线松了 / 被拔 | 插回 + `iphone-control status` |
| 3020 根页 `000` | 整页渲染炸了（多为编码错误） | 看 `proxy-3004.log` traceback，回滚 `.bak-*` |

## 7. 加一张新卡（7 步）

1. 手机启用一次该卡，记下它在捷径号码选择器里的名字。
2. 服务端登记：hw 上发 `http://127.0.0.1:3105/phone/plans?data=<双次URL编码JSON数组>`，每条 `{"name","alias","number","role"}`；`role` = `switch`（可远程切）/ `always_on`（常开，无按钮）/ `data_only`（流量，无按钮）。**整体重发数组**。
3. 2999 `/numbers` 自动多出按钮，不改代码。
4. 复制现有捷径 → 改名 → 改 4 处（三条「关闭」换成另外三条、`打开` 换目标、URL 的 `detail=/plan=` 换目标、总动作数 **5**）。
5. 建自动化：`信息 包含 "#phone on XX"` → 运行对应捷径。
6. 手动 ▶ 授权一次（运行另一个快捷指令 / 连接 push.example.com）。
7. 页面点一次验收 → 飞书应出现 `✅ 切换成功｜iPhone：卡1 固定 US；卡2 由 … 切到 **XX**`。

## 8. 安全边界

- URL 里的 token 是 32 位随机串（`mobile-push-token`），**只授权单个动作**，泄了要立刻换。
- `/phone/*` 页面端点公网必须 `ctl` 口令；`127.0.0.1` 免口令是为了让 2999 反代直接可用。
- 本方案**不改变手机的任何安全设置**：不越狱、不装描述文件、不签名、不用 Apple ID。
- 唯一有破坏性的操作是「关闭某条蜂窝线路」——捷径里绝不能出现「关闭 US（常开卡）」这类动作，改卡时必须用 a11y 坐标核对。
